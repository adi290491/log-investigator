## Methodology

- Harness: `cmd/bench`, a Go program using the go-sdk client over stdio. It starts the server process itself and connects with `mcp.IOTransport` on the process's stdin/stdout.
- Cold start: wall time from process spawn until the `tools/list` response is received (includes `initialize`).
- Workload: wall time from process spawn through `initialize`, `tools/list` and 20 sequential `error_summary` calls over 13:00-14:20 UTC.
- Calls only: the 20 `error_summary` calls alone, from the same runs.
- Peak RSS: maximum of `ps -o rss= -p <pid>` sampled every 20 ms from spawn until exit. Processes that run for less than a few sampling intervals may have their peak under-reported.
- Each server is run 10 times; the first run is discarded as warm-up. Reported as median (min-max) of the remaining 9.
- Both servers load the same `data/*.jsonl` (about 4,500 lines) into memory at startup. The Python server re-implements `internal/logstore` and returns identical counts.
- Python uses compare/python/.venv/bin/python directly (no `uv run` wrapper), so the measured process is the interpreter.
- Lines of code: `compare/loc.sh PATH...` counts non-blank, non-comment lines. Python docstrings are counted because the SDK uses them as tool descriptions.
